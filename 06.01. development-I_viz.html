6.1.1 · Where we are, and what an engine is

Before we start — Parking Lot answers from last week (two minutes). Brick 5 gave your team a loader that turns the CSV (Comma-Separated Values) file into a list of TimeEntry objects, and the skeleton files whose bodies still raise NotImplementedError: stats_engine.py, econ_engine.py, store.py, and the two abstract base classes of the tools and providers. Today two of those skeletons start to work.

An engine is the part of a program that performs the calculations; it has no screen, no file and no network — it receives numbers and returns numbers. In JARVIS, StatsEngine holds the descriptive statistics of Class 4 and EconEngine holds the formulas of Class 3. Both are written as classes with static methods: a static method (@staticmethod) belongs to the class but needs no object and no self, because the engine keeps no state between two calls — StatsEngine.mean(xs) depends only on xs.

One rule governs the whole hour: the engine is yours, the library is the oracle. A test oracle is an independent and trusted source of the correct answer, used to check a result. For us the oracle is the statistics module of the standard library: statistics.mean, statistics.median, statistics.stdev and statistics.quantiles. The engine must never call them inside its own methods, for three reasons: the Mid-Term asks you to write and explain these methods yourself; a method you wrote can be read line by line when a number looks wrong; and a check is only a check when the two sides are independent. The oracle lives in the validation table of Brick 6 (Lesson 6.4) and in the tests of Brick 9 (Class 10).

6.1.2 · mean: the formula, the one-liner and the guard

The arithmetic mean of n values is their sum divided by their count: x̄ = (x₁ + x₂ + … + xₙ) / n. In Python that is one line: return sum(xs) / len(xs). sum() adds the values, len() counts them, and the division / always produces a float — so the mean of the integers 36, 41, 48, 34 and 39 is 39.6, not 39.

The line that matters more than the formula is the guard: if not xs: raise ValueError("mean of an empty list is undefined"). An empty list is falsy in Python, so not xs is True exactly when there are no values. Without the guard, len(xs) is 0 and the division raises ZeroDivisionError — a message about division, when the real problem is the missing data. The raise statement stops the method at that line and sends an exception (an object that describes an error) to whoever called the method. ValueError is the standard exception for "the argument has the right type but an impossible value"; it is also the type that the tests of Brick 9 and the Mid-Term expect.

Why raise instead of returning 0 or None? Because a mean of 0 would silently flow into a cost calculation (0 × 28 $/h = 0 $) and nobody would notice. An exception cannot be ignored: the caller must handle it with try / except, or the program stops with a traceback that names the line. In stats_engine_part1.py the last lines show both halves: the engine raises, the caller catches and prints ValueError - mean of an empty list is undefined.

6.1.3 · median: the middle of a sorted copy

The median is the value that splits the ordered data in two halves: half of the values are at or below it, half at or above it. Two properties follow. First, the data must be sorted before you look for the middle. Second, the middle is one value when the count n is odd and the average of two values when n is even.

The first property hides the bug you will see most often this semester. Python offers two ways to sort. sorted(xs) builds a new, sorted list and leaves xs exactly as it was; xs.sort() reorders xs in place and returns None. The engine must use sorted(xs): the list it receives belongs to the caller — the loader built it in file order, and the before/after comparisons of the Results (Brick 11) depend on that order. A method that quietly reorders its argument is a method with a side effect, and side effects make a program harder to reason about.

With ordered = sorted(xs) and n = len(ordered), the index of the middle is mid = n // 2 (integer division: 55 // 2 = 27). If n % 2 == 1 (the remainder of the division by 2 is 1, so n is odd), the median is ordered[mid]; otherwise it is (ordered[mid - 1] + ordered[mid]) / 2. For the 55 manual e-mail runs, n is odd, mid is 27 and ordered[27] — the 28th value, because indexes start at 0 — is 35. For the fun-quiz list [4, 9, 1, 7] the sorted copy is [1, 4, 7, 9], mid is 2 and the median is (4 + 7) / 2 = 5.5. Take the same two positions without sorting and you get (9 + 1) / 2 = 5.0: a wrong number, produced without any error message. That is why the trap is dangerous — nothing crashes.

6.1.4 · value_range, a naming rule, and the first validation rows

The range is the largest value minus the smallest: max(xs) - min(xs). The method is called value_range and not range, because range is a built-in function of Python (the one that drives for i in range(10)); a method with the same name would shadow it — hide it inside the class — and confuse every reader. The e-mail runs span 25 to 51 minutes, a range of 26.

Mean 35.15 and median 35 are close for e-mail triage: the 55 runs are spread almost symmetrically around the centre. In Class 4 you saw the opposite case, one week with a Monday backlog of 105 minutes, where the mean (49.2) was pulled up and the median (36) stayed put. The engine does not decide which one is "the typical run"; it provides both, and the Reporter of Brick 11 prints both.

The program ends with the habit of Lesson 6.4: two lines that print the engine's value next to the oracle's value and the word match. The two values are compared with math.isclose, a comparison with a tolerance, and not with ==: two floating-point results that describe the same quantity can differ in their last digit, as Lesson 6.2 shows.

    Slide 18 · mode with Counter — and the tie you must decide

    6.2.1 · mode with Counter — and the tie you must decide

    The mode is the value that occurs most often. collections.Counter does the counting: Counter(xs) is a dictionary that maps each value to its number of occurrences, and Counter(xs).most_common(1) returns a list with the single pair (value, count) that has the highest count. For the 55 manual e-mail runs the highest count is 5 — but three values share it: 29, 32 and 37 minutes.

    A tie is not an error; it is information, and the method must say what it does with it. Three choices are defensible: return the smallest tied value, return the first one met in the data, or return all tied values. Class 4 fixed the convention for JARVIS: StatsEngine.mode returns the list of all tied values, sorted — [29, 32, 37] — so that nothing is lost and the answer does not depend on the order of the rows. The decision is written in the docstring, where the Mid-Term examiner and your teammates will read it. The module gives two answers here: statistics.mode returns only the first value it met (37 for this list, because the file order matters to it) while statistics.multimode returns all three, in order of first appearance [37, 32, 29]; the engine's sorted list is compared with sorted(statistics.multimode(xs)).

    The code is four lines: counts = Counter(xs), top = counts.most_common(1)[0][1] (the count of the most frequent value), and return sorted(value for value, count in counts.items() if count == top). The guard for the empty list comes first, as everywhere in the engine.

    Slide 19 · variance and std_dev: the n − 1 convention

    6.2.2 · variance and std_dev: the n − 1 convention

    The sample variance measures how far the values lie from their mean: s² = Σ(xᵢ − x̄)² / (n − 1). Each deviation xᵢ − x̄ is squared (so that negative and positive deviations do not cancel), the squares are summed, and the sum is divided by n − 1. The sample standard deviation s is the square root of s², back in the unit of the data (minutes).

    Why n − 1 and not n? Because the deviations are measured from the sample mean x̄, not from the unknown mean of the whole population. The sample mean sits, by construction, in the middle of the sample; the squared distances to it are therefore slightly smaller than the distances to the true population mean, and dividing by n would underestimate the spread. Dividing by n − 1 corrects that bias (the correction is named after Bessel). Our 14 days and 5 people are a sample of the studio's year, so the engine uses n − 1 — the convention of Class 4, of the Formula Card and of the Mid-Term. Python's statistics module offers both: statistics.stdev divides by n − 1 and is the oracle of the engine; statistics.pstdev divides by n and is the bug you will see in the workshop. For Set A of Class 4, [8, 10, 9, 12, 11]: deviations −2, 0, −1, 2, 1; squares 4, 0, 1, 4, 1; sum 10; variance 10 / 4 = 2.5 and s = √2.5 = 1.581. With n the results would be 2.0 and 1.414 — close enough to pass a quick look, wrong enough to fail a test.

    In code: m = StatsEngine.mean(xs), then return sum((x - m) ** 2 for x in xs) / (len(xs) - 1). The expression inside sum(...) is a generator expression: it produces the squared deviations one by one without building a list. The guard is different from the mean's: if len(xs) < 2: raise ValueError("variance needs at least two values"), because with one value n − 1 is zero. std_dev is math.sqrt(StatsEngine.variance(xs)) and needs no guard of its own.

    Slide 21 · The floating-point trap: == is the wrong question

    6.2.4 · The floating-point trap: == is the wrong question

    Python's float follows the IEEE (Institute of Electrical and Electronics Engineers) 754 standard for binary floating-point numbers: a value is stored as a binary fraction with 53 significant bits. Most decimal fractions have no exact binary representation — 0.1 is stored as 0.1000000000000000055511151231257827…, and 0.1 + 0.2 evaluates to 0.30000000000000004. So 0.1 + 0.2 == 0.3 is False, and a variance computed in two different orders of addition can differ in its last digit. The Python tutorial's chapter Floating Point Arithmetic: Issues and Limitations documents this behaviour; it is not a bug of Python, it is arithmetic in base 2.

    The consequence for the engine: never compare two floating-point results with ==. Use math.isclose(a, b), which returns True when the two numbers differ by less than a relative tolerance (by default 10⁻⁹ of their size); add abs_tol= when one of the numbers can be zero, because a relative tolerance of zero is zero. In the validation table of Lesson 6.4 the tolerance is half a unit of the last printed digit (0.005 for two decimals). In the tests of Brick 9 (Class 10) the same idea is written pytest.approx(expected). The program shows the case: the engine's standard deviation of the 55 runs is 6.352072224780001 and statistics.stdev gives 6.3520722247800006 — the same quantity, two different last digits — so == is False and math.isclose is True. A test that compares with == passes or fails by chance.

    Slide 22 · Quartiles, the IQR and the fences

    6.2.5 · Quartiles, the IQR (interquartile range) and the fences

    The quartiles cut the sorted data in four parts of equal count: Q1 has a quarter of the values below it, Q2 is the median, Q3 has three quarters below it. Several definitions exist and they give different numbers on small samples; Class 4 fixed the inclusive method, the one of statistics.quantiles(xs, n=4, method="inclusive"), of the spreadsheet function QUARTILE.INC and of NumPy's default. The rule: in the sorted copy of n values, quartile p sits at position (n − 1) × p; when that position is a whole number the quartile is the value there; otherwise it is interpolated between the two neighbours. For e-mail triage n = 55: Q1 is at position 54 × 0.25 = 13.5, halfway between the 14th and 15th values (30 and 31) → 30.5; Q3 at 40.5 → 39.5; the median at 27 → 35.

    The interquartile range is IQR = Q3 − Q1 = 9 minutes: the width of the middle half of the runs. The 1.5 × IQR rule declares an outlier any value below Q1 − 1.5 × IQR = 17 or above Q3 + 1.5 × IQR = 53. No manual e-mail run is outside those fences. The second rule of Class 4, mean ± 2 × s = [22.44, 47.85], flags two runs: 48 minutes (S3, September 14) and 51 minutes (S5, September 18). The two rules disagree, which is why your report must state the rule it used — the engine makes that explicit by taking the factor as a parameter, outliers(xs, k=1.5), and by keeping a second method outliers_sd(xs, z=2.0). Both return the flagged values in their original order, so the Reporter can say on which day they happened.

      Why does the sample variance divide by n − 1?
      answer
      Deviations are measured from the sample mean, which sits in the middle of the sample, so dividing by n underestimates the spread; n − 1 corrects the bias. statistics.stdev uses n − 1 (our oracle); pstdev uses n. Set A: 1.581 vs 1.414.

      What is the coefficient of variation for?
      answer

      Slide 29 · EconEngine: two strategies for a breaking input

      6.3.1 · EconEngine: formulas with guards, parameters instead of constants

      EconEngine turns the formulas of Class 3 into static methods. The three given numbers of the course — 28 $/h for staff time, 20 $ per user per month for the paid tier, and the free quota of the API (Application Programming Interface) tier (3 000 requests a month and 0.02 $ per request beyond it in the teaching assumptions of Class 3) — never appear inside the engine: they are parameters of the methods, so the same code answers "what if the hourly value were 32 $?" without being edited.

      The engine holds every formula of Brick 3. routine_cost(minutes, hourly_value, runs) is minutes / 60 × hourly value × runs; opportunity_cost(hours, hourly_value) is what the hours spent by hand would earn in their next-best use (one manual e-mail run of 35.15 minutes keeps 16.40 $ of billable time busy); fixed_cost(setup_hours, hourly_value) is the set-up time paid once (40 h → 1 120 $); variable_cost(requests, free_quota, price_per_request) is max(0, requests − quota) × price (3 500 requests against a quota of 3 000 at 0.02 $ → 10 $); total_cost(fixed, variable) adds the two (1 130 $); average_cost(total_cost, runs) divides by the runs (11.30 $ per run for 100 runs); marginal_benefit(minutes_saved, runs_per_month, hourly_value) is the minutes saved per run × runs × hourly value ÷ 60 (20.1 net minutes × 100 runs → 938 $ a month). Each method refuses a negative count of minutes, hours, runs or requests with a ValueError; the two methods below show the two strategies a guard can take.

      break_even_hours(monthly_price, hourly_value) returns monthly_price / hourly_value: the hours a paid tier must save each month to pay for itself. With 20 $ and 28 $/h that is 0.714 h, 43 minutes per user per month. The formula divides by the hourly value, so the method opens with a guard: if hourly_value <= 0: raise ValueError(f"hourly value must be > 0, got {hourly_value}"). An hourly value of zero is not a special case to compute; it is an impossible input, and the right answer is an exception with the offending value in its message.

      payback_months(fixed_cost, monthly_saving) returns fixed_cost / monthly_saving: a set-up of 40 hours (1 120 $ at 28 $/h) with a net saving of 910.86 $ a month is recovered in 1.23 months. Here a saving of zero is not an impossible input — a tool that saves nothing is a real possibility — and the honest answer is "never recovered". The method returns math.inf, the floating-point value for infinity: it prints as inf, it is larger than any budget of months (inf > 12 is True), and the docstring says so. The two methods show the two strategies of the lecture: an impossible input is refused with an exception; a legitimate extreme result is returned as a documented value. routine_cost(minutes, hourly_value, runs) refuses negative minutes or runs; average_cost(total_cost, runs) refuses zero runs, because an average over no runs does not exist.

      Slide 30 · SQLite: one file, one table, one language

      6.3.2 · SQLite: one file, one table, one language

      A database is a structured store of data with rules about what may enter it. SQLite is a database engine embedded in your program: no server, no installation, no account — the whole database is one file on disk, and Python ships the sqlite3 module in its standard library. That is why JARVIS can keep its data in data/jarvis.db and commit that file to GitHub (the tiny-database rule of Lesson 6.4).

      A table is a grid of rows and columns; each column has a declared type and may carry constraints. The entries table of Appendix D has one row per routine run and the columns of the CSV (Comma-Separated Values) file (date, staff_id, routine, category, start_hour, minutes, interruptions, tool, done) plus an id. Its constraints do real work: PRIMARY KEY gives every row a unique integer; NOT NULL refuses a row without a date, a staff member, a routine or a duration; CHECK (minutes >= 0) rejects a negative duration at insert time; DEFAULT 'manual' fills the tool when none is given; and UNIQUE (date, staff_id, routine, start_hour) refuses a second row with the same four values — the same run entered twice. The same key also refuses a second genuine run of the same routine by the same person started in the same hour; the LogTimeTool of Brick 7 must know that, and a team that needs finer keys adds the start minute to the schema.

      SQL (Structured Query Language) is the language of questions and orders to the data: CREATE TABLE builds the table, INSERT adds rows, SELECT asks questions. GROUP BY is the SQL equivalent of the defaultdict grouping of Lesson 6.4: SELECT routine, tool, COUNT(*), AVG(minutes) FROM entries GROUP BY routine, tool collapses the 420 rows into 8 rows, one per routine-and-tool pair, each with its number of runs and its average duration. COUNT and AVG are aggregate functions: they compute one value for a whole group.

      Slide 31 · The Store: open, use, close — every time

      6.3.3 · The Store class: open, use, close — every time

      The Store is the only class of JARVIS that speaks SQL (Structured Query Language); every other class asks the Store. Its constructor remembers the path and runs the schema with executescript(SCHEMA), which executes several statements in one call; CREATE TABLE IF NOT EXISTS makes that safe to repeat.

      Every method opens a connection and closes it, with one line: with closing(sqlite3.connect(self.path)) as con, con:. Two context managers are stacked here. closing(...) (from contextlib) guarantees that con.close() runs at the end of the block, whatever happens inside. The second, con itself, manages the transaction that the first INSERT opens: if the block ends normally the changes are committed (written to the file for good); if an exception escapes, they are rolled back (the file is left as it was). Closing a connection does not commit: rows written outside a with con: block, or without an explicit con.commit(), are discarded when the connection closes — that is the third bug of the workshop, and its other face is a write transaction left pending, which makes every other connection to the file fail with database is locked until it ends.

      Values travel into SQL through parameters: con.execute("SELECT minutes FROM entries WHERE routine = ? AND tool = ?", (routine, tool)). The values are passed to the database engine separately from the text of the query, so they can never change its meaning; gluing them into the text with an f-string is a classic error — a routine name with an apostrophe breaks the query, and a value coming from a user can turn into a command. executemany(sql, rows) runs the same INSERT once per tuple of the list rows, inside a single transaction, which is how 420 rows are loaded in a few milliseconds.

      Slide 32 · Idempotent import, GROUP BY, export, VACUUM

      6.3.4 · Idempotent import, GROUP BY, export and VACUUM

      INSERT OR IGNORE changes what happens when a row violates a constraint: instead of an error, the row is skipped — a duplicate of the UNIQUE key, but also a row that fails CHECK or NOT NULL, silently. The import_csv method therefore is idempotent — running it twice gives the same result as running it once — and it returns the row count of the table, not the number of rows inserted, so compare the count before and after an import to know what was added. The program shows it: rows after import #1: 420, rows after import #2: 420. Without the constraint every import adds another 420 rows (about 30 KB (kilobyte)); a team that imports on every start of the assistant doubles the file at each run and passes the 1 MB (megabyte) limit after a few weeks.

      avg_minutes() returns the eight rows of the GROUP BY query, and the for loop prints them with the format specs of the Reporter. The averages are identical to the means that StatsEngine computes from the same integers: SQL (Structured Query Language) AVG and Python's sum / len divide the same exact sum by the same count. They are not guaranteed to agree to the last digit when the values are floats — a sum depends on the order and the method of the additions (Python's sum adds left to right, math.fsum is exact, and a database engine uses its own algorithm) — so the comparison is written with math.isclose, like every float comparison of the engine.

      export_csv writes the table to data/export/entries.csv with the csv module (newline="" is mandatory on Windows). A CSV (Comma-Separated Values) file is text, so GitHub shows a readable diff of what changed since the last commit; a .db file is binary and shows nothing. vacuum() runs the VACUUM statement, which rebuilds the file and returns the pages that deletions left empty; it fails with cannot VACUUM from within a transaction while a transaction is pending on the connection, so the method opens a connection with isolation_level=None (autocommit: no transaction is ever pending) and closes it explicitly. After the vacuum the demo file weighs 53 248 bytes — about 5 % of the 1 MB (megabyte) limit.

        When should a method raise, and when should it return a documented value?
        answer
        Raise ValueError for an impossible input (hourly value ≤ 0 in break_even_hours). Return a documented value for a legitimate extreme result (payback_months with saving ≤ 0 returns math.inf: never recovered). The docstring states which.
        Card 2 · question
        What is SQLite, and why does JARVIS use it?
        answer
        A database engine embedded in the program: the whole database is one file, no server, and Python's sqlite3 module is in the standard library — so data/jarvis.db can be committed to GitHub and stays under 1 MB.
        Card 3 · question
        What does with closing(sqlite3.connect(path)) as con, con: guarantee?
        answer
        closing() closes the connection at the end of the block; the second manager (con) commits the transaction on normal exit and rolls it back if an exception escapes. Closing alone does not commit: rows written outside the block are lost.

        How does the import become idempotent?
        answer
        UNIQUE (date, staff_id, routine, start_hour) on the table plus INSERT OR IGNORE: a row that already exists is skipped instead of raising (so are rows that fail CHECK or NOT NULL — compare the counts before and after). Importing the CSV (Comma-Separated Values) twice leaves 420 rows, not 840.

        Slide 39 · Grouping in one pass with defaultdict(list)

        6.4.1 · Grouping in one pass with defaultdict(list)

        The Reporter needs the runs per routine, the Mid-Term needs them per staff member, and the before/after comparison needs them per day. Each grouping is a dictionary from a key (the routine name, the staff code, the date) to the list of minutes with that key. With a plain dict, the first run of a new key needs a test — if key not in groups: groups[key] = [] — before the append. collections.defaultdict(list) removes the test: when a key is read for the first time, the dictionary calls list() itself, stores the new empty list under that key and returns it. by_routine[r["routine"]].append(r["minutes"]) therefore works on the first run and on the seventieth.

        Three defaultdict(list) objects and one for loop over the rows fill the three groupings at once; len(by_routine) is 6, len(by_staff) 5, len(by_day) 14. Each list then goes to the engine: StatsEngine.mean(by_routine["email_triage"]) — all 70 runs, 30.56 minutes, pilot included — or to a filter, as in Lesson 6.1, when only the manual runs are wanted. One trap: reading a key that does not exist, by_routine["emal_triage"], does not raise — it creates an empty group, and len(by_routine) becomes 7; test with in before you read. The SQL (Structured Query Language) GROUP BY of Lesson 6.3 does the same grouping inside the database — GROUP BY routine, GROUP BY staff_id, GROUP BY date give the three groupings in one query each; the homework asks for one of the two — a small Grouper class or Store queries — not both.

        6.4.2 · The validation table: the Phase 1 scripts are the oracle

        In Bricks 3 and 4 your team wrote two scripts, econ_sheet.py and stats_sheet.py, and printed their numbers into docs/econ_notes.md and docs/stats_notes.md. Those printed numbers are now the oracle of the engines: an engine that cannot reproduce them is wrong, or the script was. The validation table of Brick 6 has one row per method: method · engine value · script value · match? — and the checkpoint asks for at least 8 green rows.

        The comparison is a math.isclose with an absolute tolerance equal to half a unit of the last digit the script printed: 0.005 for a number printed with two decimals, 0.05 for one decimal, 0.0005 for three. The program keeps that precision next to each oracle value, (18.1, 1), and computes the tolerance as 0.5 × 10^−decimals. With the uniform tolerance 0.005 the CV (coefficient of variation) row would turn red — 18.074 against 18.1 — for no reason other than the script's rounding.

        A red row is an instruction to chase the difference, in this order: rounding (the tolerance, the decimals), the formula (n or n − 1? inclusive or exclusive quartiles?), the rows that were counted (runs per month? the pilot rows?). The program shows a real case: the monthly routine bill computed over all rows is 5 607.33 $, the script printed 5 821.45 $, and no tolerance covers 214 $. The cause is a rule: Brick 3 priced the studio's current practice and left the 15 pilot runs out (tool != "jarvis"). Once the engine applies the same rule, the row is green — and the rule is now written in one place, where a test of Brick 9 will protect it. The validation table is your first unit test; the assert statements of Brick 9 (Class 10) are its rows, one per line.

        Slide 42 · f-strings and format specs: a report a person can read

        6.4.3 · f-strings and format specs: a report a person can read

        An f-string is a string literal prefixed with f in which {...} holds an expression evaluated at run time. After the expression, a colon introduces a format spec, written in Python's format specification mini-language: [fill][align][width][,][.precision][type]. {name:<14} pads the text name with spaces to 14 characters, aligned to the left (<); {value:>10.2f} writes the number in a field of 10 characters aligned to the right (>), with 2 decimals, as a fixed-point number (f). {runs:>4} right-aligns an integer in 4 characters; {ratio:.1%} multiplies by 100, keeps one decimal and adds the percent sign; {cost:,.2f} inserts thousands separators (5,821.45 for 5821.4545).

        Alignment is what makes a console report readable: the same spec on every line puts the numbers in columns, and a column of numbers is something the eye can compare. The header of the validation table uses the same widths as its rows — f"{'method':<30}{'engine':>10}{'script':>10}" — so the titles sit above the values. The Reporter skeleton of the homework is exactly this: a header, then one f-string line per routine with the mean, the standard deviation, the monthly cost and the minutes saved when automated.

        Slide 43 · The tiny-database rule and the one-writer discipline

        6.4.4 · The tiny-database rule and the one-writer discipline

        data/jarvis.db is committed to GitHub, and it is read and written by every teammate and, from December, by the scheduled job. Five habits keep that possible.

        1. Stay under 1 MB (megabyte). The 420 rows of entries weigh about 50 KB (kilobyte), and the runs table the assistant fills from Brick 7 adds a few hundred rows; a file that approaches the limit is being re-imported on every run with a plain INSERT — the UNIQUE key and INSERT OR IGNORE are there so that it cannot happen.
        2. VACUUM before every commit. Deleted rows leave empty pages in the file; VACUUM rebuilds it at its real size.
        3. One writer at a time. git pull before you run the assistant, git commit right after. Two people writing to their own copy of a binary file cannot merge the result. If a push is rejected, someone committed first: run git pull --rebase (a rebase replays your commits on top of the latest commits from GitHub); if Git reports a conflict on data/jarvis.db, take the version from GitHub — git checkout origin/main -- data/jarvis.db, then git add data/jarvis.db and git rebase --continue — and run your assistant command again so that your rows are written on top of theirs. Never merge two database files by hand.
        4. Export for readable diffs. export_csv() — python -m jarvis export — regenerates data/export/*.csv after every change, so a reviewer sees which rows changed; the .db file itself shows no diff.
        5. No secrets, no raw personal logs, no message contents in any repository; the dashboard page that GitHub Pages will publish in Sprint 2 shows aggregated numbers only. From Sprint 1 a scheduled GitHub Actions job ("the bot") runs the morning brief and commits the database back; its commit message carries [skip ci] so that the commit never triggers the test workflow.

        The rule is a non-functional requirement of Brick 2 made concrete: the database file stays under 1 MB; the assistant runs from a fresh clone with no key. It is also the Lab Proficiency dimension of the rubric — "reproducible setup; database committed and updated by the workflow" is the Exemplary level.

          Card 1 · question
          What does defaultdict(list) do that a plain dict does not?
          answer
          On the first access of a missing key it creates an empty list, stores it and returns it — so groups[key].append(x) works without an 'if key not in groups' test. Three groupings can be filled in one loop.
          Card 2 · question
          What is one row of the validation table?
          answer
          method · engine value · script value (the number the Phase 1 script printed) · match or DIFFERENT, decided by math.isclose with an absolute tolerance. Brick 6 needs at least 8 green rows.
          Card 3 · question
          How is the tolerance of a row chosen?
          answer
          Half a unit of the last digit the script printed: 0.005 for two decimals, 0.05 for one (the CV (coefficient of variation) was printed as 18.1 %), 0.0005 for three. abs_tol = 0.5 × 10^−decimals.
          Card 4 · question
          What does f"{name:<14}{value:>10.2f}" print?
          answer
          name left-aligned and padded to 14 characters, then value right-aligned in a field of 10 characters with 2 decimals. Same spec on every line = aligned columns.
          Card 5 · question
          Name the five habits of the tiny-database rule.
          answer
          Stay under 1 MB (UNIQUE + INSERT OR IGNORE); VACUUM before every commit; one writer at a time (pull before you run, commit right after, never merge two .db files); export_csv for readable diffs; no secrets, no personal logs, aggregated numbers only.
